# 쉬운 설명서 만들기 (GUIDE.md)

목적: 작업자(사용자)가 이 문서 하나만 읽고, 무엇을 왜 이렇게 만들었는지 다른 사람에게 자기 말로 설명할 수 있게 한다. 작업 중 언제든 불러도 되고, kit-wrap에서는 기능 동결 직후에 만든다. 다시 부르면 같은 파일을 최신 내용으로 덮어쓴다.

## 재료 (읽기만 한다)
- 과제 README·과제 안내, WORKLOG.md(합의·PLAN·담당자 문답·결정·해석 표·데이터 처리), REVIEW_NOTES.md, 인계 문서(있으면), `git log --oneline`, 실제 코드.
- 숫자는 기록에서 옮기지 말고 지정 실행 명령이나 짧은 스크립트로 다시 실행해서 맞춘다. 기록과 실제가 다르면 실제 값을 쓰고, 다르다는 사실을 사용자에게 먼저 알린다.

## 쓰는 규칙
- 처음 보는 사람도 읽히게 쓴다. 문장은 짧게, 한 문장에 한 가지.
- 전문 용어·약어·코드 이름은 처음 나올 때 괄호로 풀어 쓴다. 예: "재전송(MES가 같은 홀드를 몇 분 뒤 한 번 더 보낸 기록)".
- 비유 대신 이번 과제의 실제 값과 실제 예시(로트·행·항목 ID)로 설명한다.
- `파일:줄`·Q번호·R번호 같은 위치 표시는 문장 끝 괄호 안에만 둔다.
- 다른 문서를 베끼지 않는다. 같은 내용을 쉬운 말로 한 번만 쓴다. 2쪽(약 120줄) 이내.
- 사용자가 쓴 "내 판단"·합의·동작 흐름 문장은 바꾸지 않고 그대로 인용한다. 비어 있으면 "(아직 내 판단 없음)"으로 둔다.

## 목차 (이 순서 그대로)
1. **한 문장 요약**: 무엇을 만들었고, 핵심 결과 숫자가 무엇인가.
2. **용어 풀이**: 이번 과제에서 나온 말 5~10개를 한 줄씩.
3. **데이터가 결과가 되기까지**: 입력 → 거르거나 바꾼 단계(단계마다 전·후 건수) → 출력. 이어서 실제 예시 1건이 각 단계에서 어떤 값이 되는지 따라간다.
4. **내가 내린 판단**: 중요한 판단 3~5개. 각각 무엇을 정했나 / 왜(담당자 원문 한 구절이나 문서 근거) / 반대로 했다면 어떤 숫자가 몇 건 바뀌나.
5. **헷갈리기 쉬운 것**: `오해 → 사실` 형식. REVIEW_NOTES "바로잡은 이해"를 모두 포함한다.
6. **숫자 한눈에**: 핵심 결과, 기준을 바꾸면 달라지는 숫자(늘어남·줄어듦, 몇 건, 어떤 항목), 기준을 바꿀 때 고칠 곳.
7. **누가 물으면 이렇게**: REVIEW_NOTES "검토 질문" 15개마다 한두 줄 답. 사용자의 "내 판단"이 있으면 그것을 앞에 두고 근거를 붙인다.
8. **바꾼 것 목록**: 바꾼 기존 테스트(이름·전후 기대값·근거), AI가 만든 검증 도구(파일 이름·무엇을 계산하나·앱과 공유하는 가정).
9. **아직 모르는 것**: 미확정 질문과 적용한 기본 해석, 확인하지 못한 것, 다음 사람이 먼저 볼 것.

## 끝나면
- 작업 폴더에 GUIDE.md로 저장하고, 다음 코드·기록 커밋에 함께 넣는다.
- 사용자에게 한 줄로 알린다: "GUIDE.md를 읽어 보시고, 이해가 안 되는 줄을 알려 주세요." 사용자가 짚은 줄은 더 쉽게 고쳐 쓴다.
