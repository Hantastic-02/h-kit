# 웹 서비스 기본 설계 카드 (코드 없음)

과제 README가 기술 스택을 정하면 그쪽을 따른다. 자유라면 아래를 기본으로 한다. 사용자가 미리 공부해 둔 구조라서 바꾸지 않는 편이 낫다.
점검표는 둘로 나뉜다. **"항상 필수"**는 처음 뼈대(A 블록)에 넣는다. **"요구할 때만"**은 README나 담당자가 요구한 것만 C 블록에 넣는다. 요구 없는 운영 기능은 만들지 않는다.

## 기본 구성
- 서버: Python + FastAPI. **패키지 설치가 막히면** 표준 라이브러리(`http.server`, `sqlite3`, `csv`, `json`)만으로 만든다. 화면: 서버가 주는 HTML + 순수 JavaScript. 그래프는 SVG로 직접 그린다.
- DB: SQLite 파일(경로는 환경변수, 기본값 `runtime/app.sqlite3`). README가 다른 DB를 요구하면 그쪽.
- 폴더(예): `app/`(서버·계산), `app/static/`(화면), `datasets/`(준비한 데이터셋), `tests/`, `evidence/`(검증 출력), `runtime/`(DB·초기 계정, git 제외).

## 흐름 (데이터 처리형 웹 과제 공통)
1. 입력 읽기 → 2. **검증**(필수 열, 형식, ID 참조, 값 범위 — 실제 파일을 읽어서) → 3. 저장 → 4. **정제**(사유별 전후 건수를 장부로 저장) → 5. **계산**(입력 데이터 버전을 결과에 함께 저장) → 6. **화면·내보내기**.
- 데이터셋을 바꾸는 기능이 요구되면 3을 "통과하면 트랜잭션으로 적용, 버전 증가 / 실패하면 오류 목록만 보여 주고 기존 데이터 유지"로, 6에 "결과 버전이 현재 데이터 버전과 다르면 '재계산 필요' 표시"를 더한다.

## 항상 필수 (A 블록)
- [ ] **명령 한 줄로 시작**: `python -m app.server`(또는 README가 정한 명령) 하나로 빈 DB에서 켜진다. 환경변수를 안 넣어도 연습용으로는 켜진다
- [ ] **켜지면 터미널에 출력**: 주소, `/health` 주소, (계정이 있으면) 시험 계정을 볼 곳, 현재 데이터 버전
- [ ] 서버는 0.0.0.0에 바인딩, 포트는 환경변수(기본값 있음)
- [ ] `/health`가 DB 연결까지 확인해 응답한다
- [ ] 빈 DB에서 시작하면 테이블과 초기 데이터가 자동으로 준비된다. 껐다 켜도 결과가 남는다
- [ ] **실행 안내는 터미널 종류별로**: cmd는 `set NAME=값`, PowerShell은 `$env:NAME='값'`, bash는 `export NAME=값`. PLAN 1절의 종류를 먼저 쓴다
- [ ] 미리보기 창에서 열린다: `X-Frame-Options: DENY`, `frame-ancestors 'none'`을 쓰지 않는다
- [ ] 오류는 그대로 읽힐 문장으로: "items.csv 3행: 필수 열 item_id 없음 — 기존 데이터를 유지했습니다"
- [ ] **정제 장부**: 거르고 바꾼 건수가 사유별로 화면과 내보내기 기록에 같은 숫자로 보인다
- [ ] 결과에 어느 입력 데이터·조건으로 만들었는지 함께 저장
- [ ] 원본 데이터 파일을 수정하지 않는다
- [ ] 테스트: 운영 규칙(담당자 조건 포함)과 잘못된 입력 거절을 자동 테스트로 확인한다

## 요구할 때만 (README·담당자가 요구한 것만, C 블록)
- [ ] **로그인·역할**: 역할별 권한은 화면뿐 아니라 서버에서도 막는다. 비밀번호는 해시로 저장
- [ ] **초기 계정 비밀값**: 코드에 두지 않는다. 환경변수가 없으면 첫 시작 때 임의 비밀번호를 만들어 해시로 저장하고, 원문은 터미널과 `runtime/initial_accounts.txt`(git 제외)에 한 번 출력
- [ ] **미리보기 창 로그인**: 로그인 토큰을 쿠키와 요청 헤더(Authorization) 둘 다 받는다. `SameSite=Strict` 금지. 로그아웃·계정 전환 때 이전 역할의 화면을 지운다
- [ ] **환경변수 파일**: `.env.example`에 모든 이름과 설명(값은 예시)
- [ ] **Docker**: Dockerfile 1개로 서버와 화면을 함께 실행. README가 빌드를 요구하면 `docker build` 확인, 도구가 없으면 "미확인"
- [ ] **데이터셋 선택·적용**: 트랜잭션 적용, 버전 번호와 "현재 적용된 데이터셋" 표시, 결과 버전이 다르면 "재계산 필요"
- [ ] **동시 실행**: 생성·적용은 한 번에 하나(잠금). 실행 중 다시 누르면 "실행 중" 안내. 오래된 화면에서 보낸 저장은 버전 검사로 거절(409)하고 "다시 불러오세요" 안내
- [ ] **이력**: 누가 언제 데이터 적용·조건 변경·생성·확정을 했는지 DB에 남기고 운영자 화면에서 볼 수 있다
- [ ] **업로드·저장창 금지**: 데이터셋은 서버 폴더에서 목록으로 고르고, 내보내기는 화면 표시·복사 또는 서버가 주는 다운로드 링크로

## 정답 없는 최적화 과제의 기본
- 규칙(반드시 지킬 것)과 편의(가능하면 좋은 것)를 나눈다. 규칙 위반은 0건이어야 한다. 담당자 답으로 알게 된 숨은 조건도 규칙에 넣는다.
- 단순하고 설명 가능한 방법을 먼저 끝까지(예: 욕심쟁이 방법). 개선은 그 다음.
- 결과마다 지표를 같이 보여 준다. 개선을 했다면 **기준안(단순 방법)과 최종안을 같은 입력으로 한 표에** 놓고, 좋아진 것과 나빠진 것을 모두 적는다(GUIDE 8절).
- 같은 입력이면 같은 결과가 나오게 한다(무작위를 쓰면 시드를 고정하고 적는다).
- 가중치·상한 같은 정책 숫자는 근거와 민감도(바꾸면 무엇이 달라지나)를 남긴다.
- 규칙 검사기를 앱과 따로 만들어 결과를 검사한다(내보내기 형식이 있으면 그 파일로).
