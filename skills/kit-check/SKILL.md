# kit-check — 독립 검토 (읽기 전용)

너는 이 작업을 처음 보는 검토자다. 코드와 문서를 고치지 않는다. 결과는 `evidence/check-report.md` 한 파일과 채팅 표뿐이다(GUIDE.md도 고치지 않는다).
빌드 세션이 이미 자기 검토를 했으므로, 너는 그 검토가 놓쳤을 곳을 본다.

## 사용자 작업과 겹치지 않게
- 사용자가 서버를 켜 두었을 수 있다. 그 서버와 DB를 건드리지 않고 다른 프로세스를 끄지 않는다.
- 서버를 띄워야 하면 임시 폴더의 새 DB와 다른 포트로 띄우고 끝나면 끈다.
- git에 커밋하지 않는다.

## 1. 문서만 보고 다시 계산 (PLAN·HANDOFF는 아직 읽지 않는다)
- README·데이터 설명과 PLAN.md 담당자 문답 표만 읽는다: `rg -n -A80 '담당자 문답' PLAN.md`.
- 빌드의 `evidence/independent_check.py`를 쓰지 말고 다른 방식으로 짧게 센다. 예: 규칙 3~5개만 따로 검사, 또는 결과 2~3건을 원자료에서 손으로 다시 계산.
- 담당자 원문 중 "~하면 안 돼요", "~까지", "~만", "~부터" 같은 조건이 결과에 지켜졌는지 하나씩 본다.
- 데이터를 거른 곳마다 건수가 문서와 같은지 본다.
- 최종 결론을 다른 합리적 가정으로 다시 계산한다: PLAN 6절의 처리 선택 중 담당자 원문에 없는 것을 바꿔 본다. 결론이 바뀌면 P1로 올리고 어느 가정이 뒤집었는지 적는다.

## 2. 실행 안내 따라 하기
- 과제 실행 안내를 사용자 터미널 종류(PLAN 1절) 그대로 읽고, 그 터미널 문법에 맞는지 본다.
- 처음 보는 사람이 계정·주소를 알 수 있는지 본다.

## 3. 운영 상황으로 찔러 보기
- 두 사람이 동시에 바꾸면 / 데이터 적용 중에 계산하면 / 서버 재시작 / 잘못된 자료 / 권한 없는 요청 — 실제 코드 어디서 막는지 파일:줄로.

## 4. 이제 HANDOFF.md·DECISIONS.md를 읽고 대조
- "됨"인데 실제로는 안 되는 것.
- DECISIONS.md의 설명이나 숫자가 코드·결과와 다른 곳.
- GUIDE.md: 적힌 파일:줄이 실제로 그 내용을 가리키는지, 숫자가 지금 결과와 같은지. 10절 질문 3개를 골라 답이 코드·결과와 맞는지 직접 확인한다.
- `evidence/safety_check.txt`에서 빠진 점검이 있으면 하나 골라 실제 입력을 넣어 확인한다.

## 보고
`evidence/check-report.md`와 채팅에 같은 표:
| 심각도 | 문제 | 근거(명령·값·파일:줄) | 고치는 방법(한 줄) |
- P0 실행 안 됨·데이터 훼손 / P1 규칙 위반·필수 요구 실패 / P2 문서와 코드 불일치 / P3 다듬기
- 마지막 줄: "빌드 세션에 `$kit-fix`를 부를 때 이 파일을 같이 넘기세요."
