# kit-check — 병렬 독립 검토 (10분, 읽기 전용)

너는 이 작업을 처음 보는 검토자다. 코드와 문서를 고치지 않는다. 결과는 `evidence/check-report.md` 한 파일과 채팅 표뿐이다.
빌드 세션이 이미 자기 검토를 했으므로, 너는 **그 검토가 놓쳤을 곳**을 본다.

## 사용자의 화면 확인과 겹치지 않게
- 사용자가 서버를 켜 두고 있을 수 있다. 그 서버와 DB를 건드리지 않는다. 다른 프로세스를 끄지 않는다.
- 네가 서버를 띄워야 하면 **임시 폴더의 새 DB와 다른 포트(예: 8100)** 로 띄우고 끝나면 끈다.
- git에 커밋하지 않는다(빌드 세션이 곧 수정 커밋을 한다).

## 1. 문서만 보고 규칙 검사 (PLAN·HANDOFF는 아직 읽지 않는다)
- README·스키마·데이터 설명과 PLAN.md "담당자 문답" 표만 읽는다: `rg -n -A40 '담당자 문답' PLAN.md`.
- 빌드의 `evidence/independent_check.py`를 쓰지 말고, 직접 다른 방식으로 짧게 센다(예: 다른 규칙 3~5개만, 또는 샘플 2~3개를 손으로 재계산). 같은 결론이 나오는지 본다.
- 담당자 원문 중 "~하면 안 돼요", "~까지", "~만" 같은 조건이 결과에 지켜졌는지 하나씩.

## 2. 실행 안내 따라 하기
- 과제 실행 안내를 사용자 터미널 종류(PLAN 1절) 그대로 읽고, 그 터미널에서 문법이 맞는지 본다(cmd에서 `$env:` 같은 것).
- 처음 보는 사람이 계정·주소를 알 수 있는지. 미리보기 창(쿠키 차단·iframe)에서 로그인이 될 구조인지.

## 3. 운영 질문으로 찔러 보기
- 두 사람이 동시에 바꾸면 / 데이터 적용 중 계산하면 / 서버 재시작 / 잘못된 자료 / 권한 없는 요청 — 실제 코드 어디서 막는지 파일:줄로.

## 4. 이제 HANDOFF.md·GUIDE.md를 읽고 대조
- "됨"인데 실제로는 안 되는 것. GUIDE 9절 서술형 카드가 코드와 다른 곳(이게 서술형 감점의 원인이 된다).

## 보고
`evidence/check-report.md`와 채팅에 같은 표:
| 심각도 | 문제 | 근거(명령·값·파일:줄) | 고치는 방법(한 줄) |
- P0 실행 안 됨·데이터 훼손 / P1 규칙 위반·필수 요구 실패 / P2 설명과 코드 불일치 / P3 다듬기
- 마지막 줄: "빌드 세션에 `$kit-fix`를 부를 때 이 파일을 같이 넘기세요."
