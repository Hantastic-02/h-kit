# kit-frame — 과제 파악과 담당자 질문

목표: 구현 전에 "무엇을 해야 하고, 무엇을 아직 모르는지"를 숫자로 드러내고 담당자 질문을 준비한다. 코드는 바꾸지 않는다. 합의와 PLAN은 담당자 답을 받은 뒤 `$kit-plan`에서 한다.

## 1. 읽기와 환경 (읽기 전용)
- README·과제 안내·파일 목록·데이터 이름과 크기·제출물 형식과 경로·지정 실행 명령·과제가 지정한 문서 이름.
- 환경: `pwd; git status --short | head; python3 -V; node -v; date '+%F %T %Z'`. 저장소가 아니면 `git init`을 제안만 한다.
- 과제 안에 점검 스크립트(check_setup 등)가 있으면 사용자에게 실행을 안내하고, 새로 생긴 안내 문서를 읽는다.
- 과제에 AGENTS.md가 이미 있으면 요약하고 이 키트 규칙과 충돌하는 곳을 알린다.

## 2. 유형과 렌즈
- 유형을 고른다: 데이터 처리(판정·집계·파이프라인) / 웹 서비스·화면 / 기존 코드 수정 / 원인 분석·보고. 섞이면 두 개까지.
- 고른 유형의 `~/kit/lenses/<data|web|codefix|analysis>.md`를 읽고 그 관점으로 3~5를 한다. 고른 이유를 한 줄로 말한다.

## 3. 요구 정리 → WORKLOG "요구사항" 표
- 요구마다 R 번호, 출처(`파일:줄`), 수용 기준(숫자나 관찰 가능한 동작). 단계 칸은 비워 둔다.
- 요약 4줄: 목표 / 필수 요구와 제외 / 제약 / 추천 접근 1개와 버린 대안 1개.

## 4. 함정과 해석이 갈리는 곳 (데이터·코드로 센다, 추측 금지)
- 렌즈의 함정 관점에 더해 공통 관점: 빈틈, 불일치(문서 예시 값이 규칙과 안 맞는 곳 포함), 미사용 컬럼, 기준값과 정확히 같은 값, 표시 반올림 경계(.x5), 시간대·기간 경계, 중복·재전송, 늦게 붙은·미래 기록.
- 항목마다 근거 위치, 영향 건수, 예시 1개, "문서로 확정 / 데이터로 확정 / 담당자만 앎". 영향 큰 순으로 상위 6개만.
- 해석이 둘 이상이면 짧은 스크립트로 해석별 결과를 계산해 WORKLOG "해석이 갈리는 곳" 표에 차이 건수를 적는다.

## 5. 담당자 질문 초안 (사용자가 직접 보낸다)
- 사용 방식 질문 2개는 영향 건수와 상관없이 반드시 넣는다(렌즈의 사용 질문에서 고름). 숨은 요구(링크 공유, 결과를 받는 사람, 형식)는 대부분 여기서 나온다.
- 이어서 "담당자만 앎" 함정 질문 최대 4개: 한 질문에 하나, 대상 건수, 답이 없을 때 적용할 기본 해석.
- 한 메시지에 질문 하나씩 보내라고 안내한다. "확인해 보겠다"는 [미확정]이며 같은 질문을 다시 내지 않는다.

## 끝
- WORKLOG "지금"을 덮어쓰고 커밋한다: `frame: 요구 R1~Rn, 함정 n개, 질문 n개`.
- 다음 안내: 담당자 답 원문을 붙여 넣고 `$kit-plan`.
