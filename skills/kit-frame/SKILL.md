# kit-frame — 과제 정의

목표: 구현 전에 "무엇을, 왜, 어디까지 만들고, 무엇으로 확인할지"를 사용자와 합의한다. 코드는 바꾸지 않는다.

## 1. 읽기와 환경 (읽기 전용)
- README·과제 안내·파일 목록·데이터 파일 이름과 크기·제출물 형식과 경로·과제가 지정한 문서 이름을 확인한다.
- 환경: `pwd; git status --short | head; git --version; python3 -V; node -v; date '+%F %T %Z'`
  - 저장소가 아니면 과제 안내를 보고 `git init`을 제안한다. 없는 도구는 대체 방법을 한 줄로 제안한다.
- 과제에 이미 AGENTS.md가 있으면 그 내용을 요약하고, 이 키트 규칙과 충돌하는 곳을 알린다.

## 2. 요약 (짧게)
- WHY 목표 / WHAT 필수 요구와 제외 / WHERE 환경·제약·확인 안 된 것
- HOW 추천 접근 1개, 대안 1개와 버린 이유
- 요구마다 R 번호, 출처, 수용 기준(숫자나 관찰 가능한 동작) → WORKLOG "요구사항" 표
- 과제 유형 판단: 구현(웹·API·CLI) / 데이터 처리(판정·집계·원인 분석) / 기존 코드 수정 / 섞임

## 3. 함정 후보 (상위 5개, 표)
- 문서의 흔적: 데이터에 있는데 규정에 안 쓰이는 컬럼, 버전·변경 문구, "단,"·예외 문구, 상태 정의의 후속 행동, README 배경의 고충
- 명세·데이터: 빈틈(경계·단위·범위·우선순위·누락 처리), 불일치, 미사용, 쏠림(기준값과 정확히 같은 값의 빈도), 변경
- 앱: 정상 경로, 경계값, 잘못된 입력, 상태 유지, 모듈 연결, 앱 시작
- 항목마다: 근거 위치, 영향 건수, 예시 1개, "문서로 확정 / 데이터로 확정 / 담당자만 앎"
- 데이터가 있으면 짧은 스크립트로 세어서 쓴다. 추측으로 건수를 쓰지 않는다.

## 4. 담당자 질문 초안 (사용자가 직접 보낸다)
- 순서: ① 최근 실제 사례 ② 지금은 어떻게 처리하나 ③ 성공을 어떤 숫자로 아나 ④ 누가 쓰고, 안 되면 누가 얼마나 손해인가 ⑤ 예외·건드리면 안 되는 것 ⑥ 문서에 없는 고객·제품별 예외, 자주 틀리는 부분, 최근 바뀐 점
- 이어서 "담당자만 앎" 함정을 질문으로: 한 질문에 하나, 대상 건수, 답이 없을 때 적용할 기본 해석(확정 문장의 문자 그대로).
- 영향 건수가 0인 질문은 빼고, 한 번에 최대 5개만 낸다.
- 받은 답은 WORKLOG "담당자 문답"에 원문 그대로, Q 번호와 함께. "확인해 보겠다"는 [미확정]이며 같은 질문을 다시 내지 않는다.

## 5. 합의 (사용자 문장 필수)
- 아래 다섯 칸의 초안을 보여주고, 사용자가 자기 말로 고쳐 쓰게 한다. 사용자가 "좋아"만 하면 무엇을 왜 고르는지 한 번 더 묻는다.
  - 문제 / 성공 기준(숫자·현재값) / 만들 것 / 안 만들 것과 이유 / 제약
- 사용자가 쓴 문장을 WORKLOG "합의" 칸에 그대로 옮긴다.
- 사용자가 원하면 합의 요약을 담당자에게 확인받을 메시지 초안을 준다.

## 끝
