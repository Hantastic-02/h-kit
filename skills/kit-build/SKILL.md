# kit-build — 구간 하나 구현

## 0. 어떤 구간인가
- 첫 호출이면 "첫 완주"다: 입력부터 제출물(또는 핵심 화면·출력)까지 가장 단순한 경로를 끝까지 한 번 돈다. 개선은 그다음.
  - 첫 완주에서 실행 방법과 전체 실행 시간을 WORKLOG "지금"에 적는다.
- 이후에는 요구 R 하나 또는 함정 하나를 한 구간으로 잡는다. 가치·위험이 큰 것부터.

## 1. 시작 전 (2줄)
- 바꿀 범위(파일)와 회귀 위험을 말한다.
- 핵심 숫자나 결과가 나오는 구간이면 사용자에게 먼저 묻는다: "실행 전에 결과를 예상해 주세요(대략이면 됩니다)." 답을 WORKLOG 증거 칸에 [예측]으로 적는다.

## 2. 구현
- 판정·계산 규칙은 코드로 고정하고, 담당자가 정한 기준값은 한 곳(설정 상수·파일)에 모은다.
- 요청에 없는 기능·추상화·설정 파일을 만들지 않는다. 필요해 보이면 `생략: X / 필요해지는 조건: Y`를 WORKLOG "안 할 일"에 한 줄.
- 서버가 필요하면 띄우지 말고 실행 명령만 알려준다.

## 3. 확인
- LOCAL → IMPACT → GLOBAL을 실제로 실행하고 상태를 적는다. 화면 확인은 HUMAN_CHECK로 남기고 사용자가 본 뒤에만 PASS.
- [예측]과 [관측]을 나란히 적는다. 크게 다르면 원인을 먼저 찾는다(함정일 가능성이 높다).
- 기준이 모호해서 결과가 갈리면 멈추고 AGENTS.md의 질문 형식으로 묻는다.

## 4. 커밋과 기록
- 검증이 끝나면 경로를 지정해 로컬 커밋한다(메시지에 무엇을 하고 무엇을 확인했는지).
- WORKLOG: 증거 E(명령·결과·`파일:줄`), 결정 D(사용자가 고른 경우 이유 원문), "지금" 갱신.

## 5. 보고 (짧게)
- 결론 / 바뀐 파일·diff 요약 / 검증 상태
- 실제 예시 1건이 처리되는 경로: 입력 값 → 중간 값 → 결과 (`파일:줄`과 함께)
- 사용자가 답해 볼 질문 1개 (이 구간에서 "왜 이렇게 했나", "어떤 입력에서 틀리나", "두 숫자가 왜 다른가" 중 하나). 사용자가 답하면 사실 오류만 짚고, 모범 답은 쓰지 않는다.

## 첫 완주가 끝나면
- 사용자에게 입력 → 처리 → 출력 흐름을 파일 이름과 함께 3줄로 써 달라고 요청한다. 사용자의 문장을 WORKLOG "동작 흐름" 칸에 그대로 옮기고, 사실 오류만 짚는다.

## 같은 실패가 두 번이면
- 멈추고 원인을 한 줄로 정리한다. 처음 어긋난 지점부터 찾는다. 필요하면 마지막 검증 커밋으로 되돌리고 다시 확인한다.

## 다음 제안
- 남은 요구가 있으면 `$kit-build`, 핵심 요구가 다 돌면 새 세션에서 `$kit-review`.
