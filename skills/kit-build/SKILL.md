# kit-build — 뼈대부터 끝까지

## 끝나는 조건
PLAN.md 7절의 모든 항목이 `[x]` 또는 `[-]`(사유)이고 F6 최종 보고를 했을 때. 멈추는 곳은 **확인 지점** 한 번뿐이다. 블록이 끝나도 보고하고 기다리지 말고 다음 칸으로 간다.

## 시작
- HANDOFF.md가 있으면 먼저 읽는다(이어서 하는 경우). HANDOFF가 git log·PLAN 체크리스트와 다르면 그것부터 알린다.
- PLAN.md 1절·5~7절과 DECISIONS.md를 읽고 첫 `[ ]` 항목부터 시작한다.

## 항목 하나를 할 때
1. 만든다. 체크리스트에 없는 기능은 만들지 않는다.
2. 확인 칸의 명령을 실제로 실행한다. 테스트를 쓰고 돌린다. 실패하면 원인부터 찾는다.
3. 데이터를 거르거나 바꾸는 곳이면 DECISIONS.md 데이터 처리 기록에 전후 건수·사유·코드 위치를 남긴다.
4. PLAN.md 그 줄을 `[x] … — 커밋 abc1234 · 결과: 숫자`로 바꾸고 경로를 지정해 커밋한다.
5. 채팅에는 한 줄만: `B03 끝 — 확인 결과 숫자`.

## 블록이 끝날 때
- HANDOFF.md 갱신: 지금 상태 / 끝난·버린 항목 / 최근 확인 숫자 / 남은 문제 / 가정 / 다음 항목.
- 이 블록에서 정한 것이 있으면 DECISIONS.md 결정 기록에 `결정 | 이유 | 버린 대안 | 바꾸면 영향`.
- GUIDE.md에서 이 블록 때문에 바뀐 절(보통 2·4·5절)만 고친다. 채팅 한 줄에 `GUIDE n절 갱신`을 붙인다.

## 확인 지점 (B 블록 끝, 한 번 멈춤)
채팅에 아래만 내고 사용자 답을 기다린다.
1. 핵심 계산을 말과 식으로, 코드 위치(파일:줄)와 함께
2. 실제 데이터 한 건 따라가기 — 계산기로 5분 안에 따라 할 수 있는 표로: `단계 | 넣는 값(원자료 파일:행) | 식 | 나온 값`. 입력은 10개 이하로 고르고(많으면 작은 묶음을 고른다) 마지막 줄은 화면·결과 파일의 값과 같아야 한다.
3. 가장 단순한 기준 방법과 같은 입력으로 비교한 표(좋아진 것과 나빠진 것 모두)
4. 지금까지의 데이터 처리 기록 요약(사유별 건수)
5. 결론 민감도 표: PLAN 6절의 "결론을 뒤집을 수 있는 처리 선택"마다 `선택 | 지금 값 | 바꾼 값 | 결론 | 바뀜?`. 결론이 바뀌는 줄은 담당자 답 원문이 있는지 표시하고, 없으면 "담당자에게 물어볼 것"으로 질문 문장을 같이 낸다.
- 마지막 문장: "이 한 건을 직접 계산해 나온 값을 알려 주세요. 맞으면 계속하고, 다르면 어디서 갈렸는지 찾습니다."
- 사용자가 값을 알려 주면 DECISIONS.md 5절에 `[사용자] ○○ 한 건 직접 계산: 값` 한 줄을 남긴다. 값 없이 '계속'이면 확인한 것으로 적지 않는다. 다르면 어디서 갈렸는지 찾아 고치고 같은 화면을 다시 낸다.
- 계속하기 전에 1~3번과 5번 내용을 GUIDE.md 3절에 쉬운 말로 옮긴다(식, 실제 한 건, 버린 방법과의 비교 숫자, 결론이 바뀌는 선택).
- 그리고 담당자에게 보낼 중간 공유 메시지 3줄을 채팅에 낸다(멈추지 않는다): 지금 되는 것 / 핵심 숫자 하나 / 확인받고 싶은 것 하나. 사용자가 보낸다. 답이나 새 요청이 오면 AGENTS.md "사용자가 중간에 말할 때"대로.

## 멈추지 않는다 — 대신 이렇게
| 상황 | 하는 일 |
|---|---|
| 해석이 갈리는 선택 | 문서 문장에 가장 가까운 쪽으로 정하고 진행. DECISIONS.md 가정 표에 추가. 최종 결론이 바뀔 수 있으면 담당자 질문 한 줄을 채팅에 내고 결론 민감도 표에 넣는다 |
| 같은 실패 2번 | `[-] 막힘: 처음 어긋난 지점 한 줄`로 두고 다음 항목. P0이면 더 단순한 방법으로 한 번 더 |
| 패키지 설치 실패 | 다시 시도하지 말고 표준 라이브러리로. PLAN 1절에 "설치 막힘" |
| 화면을 사람이 봐야 함 | REVIEW.md에 확인할 것으로 적고 진행 |
| 사용자가 중간에 말함 | 지금 항목을 끝낸 뒤 AGENTS.md "사용자가 중간에 말할 때"대로 |
| 사용자가 "마무리해" | 남은 C·D를 `[-] 버림: 사용자 요청`, 바로 E로 |

## E. 자기 검토 (버리지 않음)
같은 세션이라 완전히 독립적이지 않다. 그래서 앱 코드를 import하지 않는 방법으로 확인한다. 하위 에이전트를 쓸 수 있으면 E1은 README·담당자 원문만 준 하위 에이전트에게 맡긴다.
- E1 독립 검사 `evidence/independent_check.py`: README·데이터 설명·PLAN 5절 담당자 원문만 보고 짠 검사기로 결과의 규칙 위반을 센다. 앱과 같은 가정을 쓴 곳은 결과에 적는다. 규칙 위반 수만 세지 말고, PLAN 6절의 처리 선택을 **다른 합리적 값**으로 바꿔 최종 결론을 다시 계산하고 결론이 같은지 적는다. 달라지면 E7에서 담당자 답 원문과 대조한다.
- E2 실행 안내를 그대로 따라 빈 상태에서 시작한다. 사용자의 서버·DB는 건드리지 않고 임시 폴더의 새 DB와 비어 있는 다른 포트를 쓴다. 헬스체크 확인 뒤 끈다. 입력 파일 복사본의 행 순서를 섞거나 일부 기간만 남겨 다시 돌려도 오류 없이 결과가 나오는지, 코드에 특정 ID·날짜·건수가 박혀 있지 않은지 본다.
- E3 역할별 주요 흐름을 실제 요청으로 끝까지 보낸다. 권한 없는 요청을 서버가 거절하는지 본다.
- E4 데이터셋 기능이 있으면: 정상 변경 → 결과가 바뀜 / 잘못된 입력 → 무엇이 틀렸는지 안내 + 기존 결과 유지.
- E5 요구 표의 R마다 됨 / 일부 / 안 함(이유).
- E6 안전 점검: 아래 중 이 결과물에 해당하는 것을 실제 입력을 넣어 확인하고 `evidence/safety_check.txt`에 `점검 | 넣은 것 | 결과`로 남긴다. 해당 없는 것은 이유 한 줄.
  - 빈 값·형식 오류·범위 밖 값·없는 ID를 넣으면 거절되고 기존 데이터가 남는가
  - SQL은 매개변수로 넘기는가(문자열 이어 붙이기 없음), 화면에 넣는 값은 이스케이프되는가
  - 파일 경로를 입력받으면 정해진 폴더 밖으로 못 나가는가
  - 권한이 필요한 기능을 권한 없이 서버에 직접 요청하면 거절되는가
  - 비밀번호·키가 코드·로그·git에 없는가, 비밀번호는 해시로 저장되는가
  - 같은 요청을 두 번 보내거나 동시에 바꾸면 결과가 꼬이지 않는가
  - 오류 응답에 내부 경로·쿼리·스택 정보가 나가지 않는가
  - 원본 데이터 파일이 바뀌지 않았는가(git으로 확인)
  - 결과를 GUIDE.md 6절 표로 옮긴다.
- E7 E1~E6에서 나온 실행 불가·데이터 훼손·규칙 위반·필수 요구 실패·안전 문제를 바로 고치고 그 검사를 다시 돌린다. 나머지는 HANDOFF "남은 문제"로.

## F. 문서 (버리지 않음)
- F1 REVIEW.md: 하는 일 3줄, 계정 표, 볼 순서(단계마다 왜 보나 / 하는 법 / 정상이면 보이는 것, 오류 문구 포함).
- F2 과제가 요구한 문서(실행 안내 등). 명령은 E2에서 실제로 돈 것만 쓴다.
- F3 DECISIONS.md 정리: 결정·가정·데이터 처리·변경 기록이 지금 코드와 맞는지 대조하고 고친다.
- F4 GUIDE.md 마무리: 지금 코드·결과로 1~9절을 맞추고 10절 질문 12~16개를 네 묶음(설계·정확성·운영안전·과정)에서 고루 쓴다. 답의 숫자는 실행해서 나온 값만, 근거 위치는 실제 파일:줄.
- F5 HANDOFF.md 최종 갱신.
- F6 최종 보고(채팅, 이것만):
  1. 블록별 됨/버림 수와 버린 항목 제목
  2. 자기 검토 숫자: 독립 검사 위반 수, 테스트 n passed, 실행 확인 여부, 안전 점검 통과 n/n, 미확인 목록
  3. 가정 목록(이번에 새로 생긴 것 표시)
  4. 다음: "GUIDE.md 2·3절을 먼저 읽고, REVIEW.md 순서대로 화면을 직접 보세요. 터미널이 남으면 새 세션에서 `$kit-check`. 본 것과 이상한 점을 모아 이 세션에 `$kit-fix`."
