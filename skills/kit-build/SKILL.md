# kit-build — PLAN 한 단계

## 0. 대상 단계
- 사용자가 고른 단계(예: `$kit-build S2`), 없으면 PLAN의 첫 "대기" 단계.
- 그 단계의 할 일·완료 조건을 그대로 보여 주고 상태를 "진행"으로 바꾼다. 앞 단계가 완료가 아니면 알리고 사용자가 정하게 한다.

## 1. 시작 전 (2줄)
- 바꿀 파일과 회귀 위험.
- 숫자·판정이 나오는 단계면 사용자에게 먼저 묻는다: "실행 전에 결과를 예상해 주세요(대략이면 됩니다)."

## 2. 구현
- 기준값은 상수 한 곳에 모은다. 요청에 없는 기능·추상화는 만들지 않는다(필요해 보이면 PLAN 뒤 단계에 할 일로 제안).
- 서버는 띄우지 않고 실행 명령만 알려 준다.

## 3. 확인 (완료 조건을 하나씩)
- 완료 조건마다 실제로 실행해 확인한 것만 체크한다. 실패면 체크하지 않고 원인부터 찾는다.
- 테스트 기대값에 출처 주석: `# 기대값: 담당자 Q-2 원문` / `# README 예시` / `# 사용자 손계산` / `# 내 해석`.
- 고친 곳 → 연결된 기능 → 지정 실행 명령으로 핵심 흐름 순서로 확인하고, 전체 테스트를 돌린다.
- 화면·결과물은 사용자에게 볼 것을 구체적으로 준다(주소, 클릭 순서, 기대 결과). 사용자가 확인한 뒤 체크한다.
- 예측과 관측이 다르면 원인을 먼저 설명한다(함정일 가능성이 크다).

## 4. PLAN 갱신 (덮어쓰기)
- 체크박스, 단계 상태(`완료 <커밋>`), "지금", 요구사항 상태, 해석 표·데이터 처리 표의 최신값을 고친다. 진행 중 생긴 할 일은 해당·다음 단계에 체크박스로 추가한다.
- WORKLOG가 150줄을 넘으면 완료된 단계의 할 일을 한 줄로 접는다: `- [x] 할 일 6개 완료 — 커밋 abc123`.

## 5. 단계 이해 보고 (서술형 대비 — 채팅으로 보고하고 STUDY.md에 같은 내용을 절로 추가)
처음 보는 사람도 이해하도록 쉽게, 실제 값으로, 용어는 괄호로 풀어서 쓴다. 칸마다 2~4줄.
1. **이번 단계에서 주로 한 일**: 무엇을 왜 바꿨나, 바뀐 곳 `파일:줄`
2. **실제 예시 1건 따라가기**: 입력 값 → 중간 값 → 화면·출력 값 (`파일:줄`과 함께)
3. **꼭 이해할 점**: 이 단계의 핵심 규칙과 근거(R·Q 번호, 담당자 원문 한 구절)
4. **헷갈리기 쉬운 점**: `오해: … → 사실: …` 형식 2~3개. 사용자가 앞에서 틀리게 말한 것이 있으면 반드시 포함
5. **반대로 했다면**: 다른 해석·이전 코드·기준값 변경 시 어떤 숫자가 어떻게 바뀌나. 실제로 실행해서 얻은 값만
6. **예측과 결과**: 사용자 예측과 실제, 다르면 왜
7. **서술형 예상 질문 1개**: "왜 이렇게 했나 / 두 숫자가 왜 다른가 / 반대였다면 / 기준이 바뀌면 어디를 고치나" 중 이 단계에 맞는 것
- 사용자가 7에 자기 말로 답하면 STUDY에 원문 그대로 적고, 틀린 사실은 실제 값과 `파일:줄`로 바로잡아 함께 적는다. 사용자가 넘기면 "미답"으로 둔다(wrap에서 다시 묻는다).
- S1(첫 완주) 뒤에는 입력 → 처리 → 출력 흐름을 파일 이름과 함께 3줄로 써 달라고 요청하고, 사용자 문장을 WORKLOG "동작 흐름"에 그대로 옮긴다. 사실 오류만 짚는다.

## 6. 커밋
- 코드·테스트·WORKLOG·STUDY를 한 커밋으로: `S2: 무엇을 했나 / 확인: 명령 → 결과 숫자`. 사용자 답은 다음 커밋에 함께 넣는다.

## 같은 실패가 두 번이면
- 멈추고 처음 어긋난 지점을 한 줄로 정리한다. 필요하면 마지막 검증 커밋으로 `git checkout <커밋> -- <경로>` 후 다시 확인한다.

## 다음 제안
- 남은 "대기" 단계가 있으면 `$kit-build S다음`. 모두 완료면 두 번째 터미널의 새 codex에서 `$kit-review`.
