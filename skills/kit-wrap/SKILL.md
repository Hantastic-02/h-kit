# kit-wrap — 마무리와 제출 점검

새 기능은 만들지 않는다. 고치는 것은 문서의 숫자·문장과 명백한 오타뿐이다. 코드 문제를 발견하면 고치지 말고 보고에 적는다(사용자가 고치라고 하면 그때 kit-fix 규칙으로).

## 1. 처음부터 다시 실행
- 실행 안내 그대로 빈 상태에서 시작 → 전체 테스트 → E1 독립 검사 → 내보내기·결과 파일 다시 만들기.
- 나온 숫자를 HANDOFF.md·DECISIONS.md·과제 문서의 숫자와 대조한다. 다르면 문서를 지금 결과에 맞춘다.

## 2. 요구 충족표
- 요구 표의 R마다 `됨 / 일부 / 안 함 | 확인 방법(명령·화면) | 비고`.
- 과제 제출물 목록과 대조: 파일이 있는지, 정해진 양식의 절이 다 있는지, 이름이 정확한지.

## 3. 문서와 코드 맞추기
- DECISIONS.md, GUIDE.md, 실행 안내, 과제가 요구한 문서의 숫자·파일 이름·명령·설명이 지금 코드·결과와 같은지 본다. GUIDE.md의 파일:줄은 하나씩 열어 확인한다.
- 실행으로 확인하지 않은 주장은 "미확인"으로 바꾸거나 지운다. 근거(파일·명령)가 없는 문장을 남기지 않는다.

## 4. 시연 순서
- `.agents/kit/templates/DEMO.md` 양식으로 DEMO.md를 쓴다. 숫자는 1번에서 나온 값만 쓴다.

## 5. 원본 보존과 정리
- 원본 데이터와 과제 README가 바뀌지 않았는지 git으로 확인한다.
- 마무리 커밋(경로 지정): `wrap: 재실행 확인·문서 정합·제출 점검`. `git status`가 비었는지 보고, 남은 파일이 있으면 목록을 보여 준다(실행 중 생긴 DB·캐시는 제외 대상인지 확인).

## 6. 보고 (채팅)
1. 요구 충족표 요약(됨 n / 일부 n / 안 함 n)
2. 재실행 숫자와 문서에서 고친 곳
3. 남은 한계 3개(무엇을 안 했고, 하려면 무엇이 필요한지)
4. 사용자가 직접 정한 것 3개(DECISIONS.md `[사용자]` 표시와 결정 기록에서): 무엇을, 왜, 다르게 했다면 몇 건이 달라졌나
5. "GUIDE.md 3·5·6절을 읽고 핵심 계산, 거른 데이터, 안전장치를 자기 말로 한 줄씩 보내 주세요. 코드·결과와 다른 곳만 짚습니다. 그다음 제출 화면에서 파일 목록을 확인하고 제출하세요."
