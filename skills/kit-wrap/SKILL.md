# kit-wrap — 인계와 제출 준비

제출물을 확정한 뒤라면 아무것도 하지 않고 "확정 뒤에는 쓰지 않습니다"라고만 답한다.

## 1. 동결
- 새 기능·리팩터링을 멈춘다. 반쯤 만든 기능은 끄거나 빼고 한계에 적는다.

## 2. 제출물 대조 (가장 먼저)
- README·과제 안내가 요구한 필수 파일·문서·형식·경로·실행 명령과 한 줄씩 대조한다.
- 지정된 실행 명령으로 처음부터 다시 실행하고 전체 테스트를 돌린다. 결과 숫자를 보고한다.
- 빈 템플릿 행·자리표시·TODO를 찾아 알린다.
- `python3 ~/kit/bin/check.py`를 실행하고 경고를 보고한다(사용자가 직접 실행해도 된다).

## 3. 인계 문서
- 과제가 지정한 문서(README·REPORT 등, 파일명은 과제 기준)에 다음을 쓴다. 지정이 없으면 README의 "인계" 절에 쓴다.
  - 결론과 핵심 숫자 (맨 위)
  - 실행 방법과 동작 방식: WORKLOG "동작 흐름"의 사용자 문장을 바탕으로
  - 판단과 근거: 결정 D마다 무엇을, 왜, 버린 대안, 대안이었다면 달라지는 것. 출처 꼬리표 유지
  - 데이터를 걸렀거나 바꾼 지점과 전후 건수
  - 검증: 실제 명령과 결과. 하지 않은 검증은 쓰지 않는다
  - 알려진 한계·미확인·[미확정] 항목과, 다음 사람이 먼저 확인할 것
  - 사용한 공개 도구: 이 키트 저장소 이름과 용도 한 줄
- "확정"이라고 쓴 곳은 WORKLOG 담당자 문답 원문과 대조한다.

## 4. 인수자 질문 점검
- 이 작업을 넘겨받는 동료가 물을 만한 질문 3개를 낸다. 다음 중에서 실제 기록에 근거해 고른다:
  - 이 순서·구조로 만든 이유 / 두 숫자가 왜 다른가 / 다른 해석이었다면 무엇이 바뀌나
  - 이 기대값은 무엇과 맞춰 봤나 / 운영에서 어떤 입력이 오면 깨지나 / 기준이 바뀌면 어디를 고치나
  - 기록의 전제가 실제 구현과 다른 곳이 있다면 그것을 묻는 질문 1개
- 질문마다 근거 위치(`파일:줄`, R·Q·D·E 번호)만 붙이고 답은 쓰지 않는다.
- 사용자가 자기 말로 답하면 코드·기록과 대조해 사실 오류만 짚는다. 막힌 질문은 인계 문서의 빈틈이므로 문서를 보완한다.

## 5. 마무리
- 최종 상태를 커밋하고 `git status`가 비었는지 확인한다.
- 사용자에게 안내: 저장 상태 확인 → 제출 시작. 이후로는 새 작업을 시작하지 않는다.
