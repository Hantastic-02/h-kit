# kit-plan — 합의·방법·체크리스트

코드는 바꾸지 않는다. PLAN.md 4~10절, DECISIONS.md 가정 표, GUIDE.md 초안을 쓰고 승인 화면을 낸다. 승인이 가장 큰 조종 지점이다.

## 1. 담당자 답 반영
- PLAN 5절에 주제별로 묶어 `Q 질문 / A 답 원문 / → 반영(R·체크리스트 항목·가정 번호)` 형식으로 옮긴다. 답은 **원문 그대로**, 이름·숫자·조건을 바꿔 쓰지 않는다.
- 답에 따라 요구 표(R)를 고치거나 추가한다. 답이 없는 것은 DECISIONS.md 가정 표로.
- 무엇을 풀지 정해졌으면 PLAN 4절에 **합의 메시지** 5줄 초안을 쓴다: 문제 한 문장 / 누가 쓰나 / 성공 기준(숫자) / 하지 않을 것 / 제약. 사용자가 담당자에게 보내 확인받는다. 답이 오면 원문을 5절에 추가한다.

## 2. 방법 고르기 (PLAN 6절)
- `.agents/kit/cards/README.md`를 읽고 과제 모양에 맞는 카드 1~2장을 읽는다. 웹 화면이 있으면 `web-service.md`도 읽는다.
- 핵심 계산 방법 후보 2개를 표로 비교한다. 그중 하나는 가장 단순한 기준 방법이다: `방법 | 무엇을 계산 | 장점 | 약점 | 설명하기 쉬운가 | 걸리는 시간`. 하나를 추천한다.
- 카드의 "함정 점검"을 이번 데이터와 담당자 답에 대입해, 해당하는 것만 체크리스트 항목으로 옮긴다. 해당 없는 것은 옮기지 않는다.
- 정책 숫자: `숫자 | 근거 | 바꾸면 무엇이 달라지나`. 근거가 없으면 "근거 없음"이라고 쓰고 민감도 확인을 C나 D 항목으로 넣는다.
- **결론을 뒤집을 수 있는 처리 선택 2~4개**를 고른다. 숫자 기준만이 아니라 처리 방식도 본다: 여러 층·항목의 결과를 합치는 규칙(하나라도 / 가중 합 / 다수), 최소 표본 수, 제외 기간의 시작·끝, 다시 기록된 건 중 어느 것을 쓰나, 이상의 시작 시점.
  - 표로 쓴다: `선택 | 후보 값 | 담당자 답(Q번호) / 가정 | 바꾸면 결론이 어떻게 달라질 수 있나`.
  - 담당자 답이 없는 선택은 9절 추가 질문으로 만든다(기본 해석 포함). 답이 와도 원문에 없는 부분은 가정으로 남긴다.
  - B 블록에 "결론 민감도" 항목을 하나 넣는다: 이 선택들을 다른 합리적 값으로 바꿔 결론을 다시 계산한 표.
- `.agents/kit/templates/GUIDE.md` 양식으로 GUIDE.md를 만들고 1절(요약)과 3절의 "한 줄로·왜 이 방법인가·버린 방법"을 쉬운 말로 초안한다. 숫자 칸은 빌드에서 채운다.

## 3. 빌드 체크리스트 (PLAN 7절, 15~25개)
- 순서: A 뼈대(처음부터 끝까지 한 번 도는 최소 버전, 3~5개) → B 핵심 계산·규칙(4~8개, 첫 항목은 데이터 처리 기록) → **확인 지점** → C 나머지 요구(3~6개) → D 개선(0~3개) → E 자기 검토(양식 그대로) → F 문서(양식 그대로).
- 항목 하나 = 기능 하나 + 그것을 판정하는 확인 하나. 형식: `- [ ] B03 P0 (R4) 무엇 — 확인: 명령 → 기대값`.
- 확인 칸은 실행해서 숫자·상태로 판정할 수 있어야 한다. "잘 동작" 금지.
- 담당자 답으로 알게 된 규칙은 B 항목과 E1 기대값 양쪽에 넣는다.
- A에는 web-service.md "항상 필수"만. "요구할 때만" 항목은 요구된 것만 C에. "화면 기본"은 항목을 따로 늘리지 말고 화면을 만드는 항목의 확인 칸에 넣는다.
- 사용자가 낸 아이디어는 P1 이상으로 넣고 출처를 "사용자"로 적는다.
- 고칠 기존 코드가 있으면: C나 E에 "수정 전·후 비교표(`evidence/before/`와 같은 입력, 바뀐 칸 수와 이유)" 항목을 넣는다. 기존 테스트가 문서·담당자 답과 다르면 테스트를 고치는 항목으로 넣고 근거를 DECISIONS.md 결정 기록에 적는다.

## 4. 대조 (PLAN 8절)
- 실제로 센다: R → 항목 n/n, 담당자 규칙 → B와 E1 n/n, 결론을 뒤집는 선택 → 담당자 질문과 B 민감도 항목 n/n, 확인 칸 판정 가능 n/n, 경계 조건(기간 앞뒤, 0건·빈 값, 기준값과 정확히 같은 값), 요구 없는 기능이 빠졌나.
- 빠진 것은 고치고 "고침"으로 남긴다. 고칠 수 없는 빈틈(모르는 것)은 9절 추가 질문 3~5개로 만들고 기본 해석을 붙인다.
- 10절에 가장 위험한 항목과 막히면 대신할 단순한 방법을 쓴다.

## 5. 승인 화면 (채팅, 짧게)
전체 체크리스트는 PLAN 7절에 있다고만 말하고 아래만 보여 준다.
1. 문제 한 문장과 성공 기준
2. 읽은 방법 카드 이름, 고른 방법과 버린 방법(각 한 줄, 이유 포함)
3. 결론을 뒤집을 수 있는 처리 선택 목록: `선택 | 지금 값 | 담당자 답 / 가정`
4. P0 항목 제목 목록
5. 가정 목록
6. 대조 결과(고친 것 포함)
7. 추가 질문 — 3번 선택에 관한 것은 "승인 전에 지금 보내세요", 나머지는 "빌드 중에 보내세요"
8. 가장 위험한 항목과 대신할 방법
9. 물음: "빠진 요구, 틀린 가정, 넣고 싶은 기준이 있나요? 3번 선택 중 담당자에게 더 물어볼 것이 있나요?"
- 끝: "승인하면 `$kit-build`로 진행합니다. 핵심 계산이 끝나면 한 번 멈춰 실제 한 건을 같이 확인합니다."
