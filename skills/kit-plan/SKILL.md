# kit-plan — 빌드 체크리스트와 자기 점검

코드는 바꾸지 않는다. PLAN.md 4절의 답을 채우고 5~11절을 `.agents/kit/templates/PLAN.md` 양식으로 쓴다. 계획 승인이 사실상 **유일한 중간 조종 지점**이다. 빌드는 이 목록대로 끝까지 간다.

## 1. 담당자 답 반영
- 4절 표의 답 칸에 **원문 그대로** 옮긴다. 사람 이름·숫자·장소를 바꿔 쓰지 않는다.
- 답에 따라 요구 표(R)를 고친다. 새 요청은 R로 추가한다.
- "답 없음"은 5절 가정 표로: 문서 문장에 가장 가까운 해석, 근거, 틀리면 바뀌는 것.

## 2. 판단 기준 (6절, 정답이 하나가 아닌 과제)
- "무엇을 더 좋다고 볼지" 우선순위 3~5개와 출처.
- 설명할 수 있는 단순한 방법을 고른다. 버린 대안 1개와 이유 한 줄.
- 가중치·상한 같은 정책 숫자는 `숫자 | 근거 | 바꾸면 무엇이 달라지나`. 근거가 없으면 "같은 비중(근거 없음)"처럼 정직하게 쓰고, 민감도 확인을 C나 D 항목으로 넣는다.

## 3. 빌드 체크리스트 (7절, 15~25개)
- 블록 A(최소 실행 P0) → B(핵심 계산·규칙 P0) → C(나머지 요구 P1) → D(개선 P2) → E(자기 검토, 고정) → F(문서, 고정).
- 항목 하나 = 기능 하나 + 그것을 판정하는 확인 하나. 형식: `- [ ] B03 P0 (R4,R7) 무엇 — 확인: 명령 → 기대값`.
- **확인 칸은 실행해서 숫자·상태로 판정할 수 있어야 한다.** "잘 동작" 금지.
- A에는 `.agents/kit/design/web-service.md`의 **"항상 필수"**만 넣는다. 로그인·역할·잠금·이력·Docker 같은 **"요구할 때만"** 항목은 README나 담당자가 요구한 것만 C에 넣는다.
- B를 A 바로 뒤에 둔다. 핵심 계산이 결과 정확도의 대부분이다. B 첫 항목은 정제 장부다.
- 숨은 조건(담당자 답으로 알게 된 규칙)은 P0 규칙 항목과 E1 기대값 양쪽에 넣는다.
- 사용자가 계획 검토 중 낸 아이디어는 P1 이상으로 넣고 출처를 "사용자"로 적는다.
- E·F는 양식 그대로 두되, E1·E3·E4의 기대값을 이번 과제 숫자로 바꿔 적는다.

## 4. 자기 점검 (8~9절)
- 8절 대조표를 실제로 센다: R → 항목, 담당자 규칙 → P0 + E1, 확인 칸 판정 가능 여부, 경계 조건, 운영 기능 범위. 빠진 것은 고친 뒤 표에 "고침"으로 남긴다.
- 고칠 수 없는 빈틈(모르는 것)은 항목을 늘리지 말고 9절 **추가 질문** 3~5개로 만든다. 질문마다 기본 해석을 붙인다.
- 10절 사용자 검토 예정, 11절 가장 위험한 항목을 쓴다.

## 5. 승인 화면 (채팅, 짧게)
전체 체크리스트는 PLAN 7절에 있다고만 말하고, 아래만 보여 준다.
1. P0 항목 제목 목록(한 줄씩)
2. 가정 목록(한 줄씩)
3. 대조표 결과(고친 것 포함)
4. 추가 질문 3~5개 — "빌드 중에 담당자에게 보내세요"
5. 가장 위험한 항목과 막히면 대신할 방법
6. 사용자에게 묻기: "빠진 요구·넣고 싶은 아이디어가 있나요? P1인데 꼭 있어야 하는 것이 있나요? 틀린 가정이 있나요?"
- 끝에: "승인하면 `$kit-build`로 한 번에 끝까지 갑니다. 중간에 바로 반영할 것이 생기면 그냥 말씀하세요."
