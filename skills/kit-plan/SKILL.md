# kit-plan — 합의와 PLAN

## 1. 담당자 답 반영
- 사용자가 준 답을 WORKLOG "담당자 문답"에 원문 그대로, Q 번호와 과제 시작 후 분으로 적는다. 요약하거나 고치지 않는다.
- 답에 따라 요구사항 표(R 추가·수용 기준 수정), "해석이 갈리는 곳"의 현재 적용, "미확정·한계"를 고친다. 지난 초안은 지운다(git에 남는다).
- 답에 새 요청(추가 기능)이 있으면 R로 추가하고 사용자에게 알린다.

## 2. 합의 (사용자 문장)
- 다섯 칸 초안(문제 / 성공 기준(숫자) / 만들 것 / 안 만들 것과 이유 / 제약)을 보여 주고 사용자가 자기 말로 고쳐 쓰게 한다.
- 사용자가 "그대로"라고 하면 성공 기준과 "안 만들 것의 이유" 두 칸만이라도 직접 써 달라고 한 번 더 요청한다. 그래도 넘기면 `[내 결정: 초안 채택]`으로 적고 진행한다.

## 3. PLAN 작성 (WORKLOG "PLAN" 절, 상세하게)
- 단계는 4~7개. S1은 첫 완주(입력 → 제출물·핵심 화면까지 가장 단순한 경로를 끝까지). 이후 단계는 가치·위험이 큰 요구부터.
- 단계마다 다음을 쓴다:
  - 제목 줄: `### S2 이름 — 상태: 대기 — 예산 __분`
  - 목표 한 줄, 관련 R·Q
  - 할 일 체크박스: 파일·함수 단위로 구체적으로
    예) `- [ ] app/server.py 상태 재생에서 이미 홀드 중인 로트의 HOLD는 시작 시각을 바꾸지 않음`
  - 완료 조건 체크박스: 숫자나 관찰 가능한 결과
    예) `- [ ] 05:50 HOLD → 06:03 재전송 → 09:00 조회 시 시작 05:50, 오늘 신규 1`
  - 확인 방법과 기대값 출처: 명령·테스트 이름, 기대값이 어디서 왔는지(`담당자 Q-n 원문` / `README 예시` / `사용자 손계산` / `내 해석`)
  - 사용자 확인: 화면이나 결과물에서 사용자가 직접 볼 것
- 점검: 모든 R이 어느 단계에 배정됐나(요구사항 표의 단계 칸을 채운다), "해석이 갈리는 곳"마다 테스트 할 일이 있나, 사용 질문에서 나온 요구가 빠지지 않았나.
- 확인할 수 없는 항목은 `[기본 해석]`과 근거를 결정 표에 적는 할 일로 넣는다.
- PLAN 머리에 기능 동결 시각과 제출 시작 시각을 적는다. "마무리 체크"는 템플릿 그대로 둔다.

## 4. 승인
- PLAN을 단계별 2~3줄로 요약해 보여 주고 사용자 승인을 받는다. 사용자가 바꾼 순서·범위는 이유와 함께 결정 표에 적는다.
- "지금"을 갱신하고 커밋한다: `plan: 합의·PLAN S1~Sn`.
- 다음 안내: `$kit-build S1`.

## build 중에 PLAN 고치기
- 새로 발견한 할 일은 해당 단계에 체크박스로 추가하고, 범위가 크면 새 단계를 만든다.
- 시간이 모자라면 뒤 단계를 `보류(이유)`로 바꾸고 결정 표에 한 줄. 서술형 리허설 시간은 줄이지 않는다.
