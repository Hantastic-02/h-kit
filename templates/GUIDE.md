## 0. 5분 요약 (외울 것)
- 이 서비스가 하는 일 한 문장.
- 핵심 숫자 5개: 결과 규모, 규칙 위반 수, 정제로 빠진 건수(사유별 상위 3개), 테스트 수, 독립 검사 결과.
- 내가 내린 판단 3개: `○○로 했다 / 이유 / 버린 것`.
- 담당자에게 확인한 것 3개, 끝내 모른 것과 가정 3개.
- 동시에 두 사람이 바꾸면 실제로 무엇이 막는지 한 줄.

## 1. 한 장 그림 — 데이터가 결과가 되기까지  (서술형: 데이터 흐름)
```
입력 파일 → 검증 → 저장 → 정제(빠진 건수) → 계산 ①②③ → 결과 저장(버전) → 화면 / 내보내기
```
- 칸마다 한 줄: 무엇을 하나, 몇 건이 들어가고 몇 건이 나오나.
- **원자료 한 행 따라가기**: 실제 한 행(예: 한 사람의 한 기록)이 각 칸에서 어떤 값이 되는지.
- "어디서 보나" 표: 궁금한 것 | 파일 | 함수.

## 2. 기능별 카드  (서술형: 어디를 보나)
요구 하나에 카드 하나. 빌드가 블록마다 추가한다.
- **R번호 이름**: 무엇을 / 왜 필요한가(누가 쓰나) / 어떻게 동작하나(3줄) / 파일·함수 / 확인 방법과 결과 숫자

## 3. 설계 기준과 이유  (서술형: 왜 이 방식인가)
- "더 좋은 결과"의 기준 3~5개와 우선순위, 각각의 출처.
- 고른 방법을 단계 목록으로 쓰고, 실제 한 건(예: 한 항목, 한 날짜)이 그 단계를 지나는 모습을 숫자로 보여 준다. 버린 방법과 이유.
- 점수·지수 같은 계산은 식을 쓰고, 실제 한 건의 값을 대입해 결과 숫자까지 계산한다.
- 정책 숫자 표: `숫자 | 근거 | 바꾸면 무엇이 달라지나`. 근거가 없으면 없다고 쓴다.
- 이 방법이 못하는 경우(한계)와 시간이 있으면 할 개선.

## 5. 운영 질문 대비  (서술형: 동시성·장애·검증 실패)
- 두 사람이 동시에 바꾸면: 실제 구현된 것만(잠금·버전 검사·트랜잭션). EASY.md 예시처럼 **시각 순서로 한 장면을 따라가며** 누가 무엇을 누르고, 무엇이 거절되고, 막힌 사람은 다음에 무엇을 하고, 사용자에게는 어느 판이 보이는지 쓴다.
- 사용자가 보는 결과가 어느 데이터 버전인지 어떻게 보장하나.
- 서버 재시작 / 잘못된 데이터 / 빈 DB.
- 검증에서 깨지면 볼 순서: ① 입력 데이터·버전 ② 어떤 규칙이 몇 건 ③ 그 규칙을 계산하는 함수 ④ 재현 테스트 → 수정 → 전체 테스트·독립 검사.
- 구현하지 않은 것은 "하지 않았다, 운영이라면 ○○을 하겠다".

## 6. 용어 사전
서술형에서 그대로 쓸 **정식 용어** 8~12개(예: 트랜잭션, 잠금, 버전 충돌, 정규화, 헬스체크). 지어낸 우리말을 넣지 않는다.
| 정식 용어 | 쉬운 뜻 한 줄 | 이번 과제에서 어디에·무엇에 쓰였나 |
|---|---|---|

## 7. 헷갈리기 쉬운 것
`오해 → 사실`. 사용자가 검토·연습 중 틀리거나 "이거 정상이야?"라고 물은 것을 모두 넣는다.

## 8. 숫자 한눈에
핵심 결과 숫자(실행해서 얻은 값), 기준안과 최종안 비교(좋아진 것과 나빠진 것 모두), 조건을 바꾸면 늘고 주는 것, 바꿀 때 고칠 곳.
